# 部署与发布：第一阶段（本地部署基座）

已建立可复现的部署基座，并添加 GitHub Actions CI。常驻测试环境、自动发布、权限、备份和正式发布门禁尚未实现。
正式服目前是手工部署版本；本分支没有更新正式服。

## 文件职责

- `Dockerfile`：用 npm ci 从源码构建前端，再制作 Python 3.12 应用镜像。运行时不需要 Node。
- `.dockerignore`：白名单构建上下文，不发送密钥、Git 历史、图片或本机依赖。
- `compose.deploy.yml`：应用与 PostgreSQL 17；数据库不暴露端口，应用只绑定本机。
- `compose.https.yml`、`Caddyfile`：可选 HTTPS 入口，证书持久化。
- `deploy.env.example`：无密钥环境配置示例。
- `scripts/init-local.py`：创建独立本地配置和随机数据库密码，可重复运行，不覆盖旧文件。
- `scripts/deploy.sh`：显式的构建、建库、迁移、启动和检查命令。仅用于 Linux/WSL/Git Bash。

应用仍必须单进程运行。Python 依赖和基础镜像尚未完全锁定；本阶段不宣称构建逐字节可复现。
原 `docker-compose.yml` 仍只用于旧本地开发数据库，不要和部署 Compose 合并。

## 本地从零验证（Windows PowerShell）

先启动 Docker Desktop，确保使用 Linux 容器，然后在仓库根目录执行：

```powershell
python scripts/init-local.py
docker compose --env-file .deploy/local.env -f compose.deploy.yml config -q
docker compose --env-file .deploy/local.env -f compose.deploy.yml build app
docker compose --env-file .deploy/local.env -f compose.deploy.yml up -d --wait db
docker compose --env-file .deploy/local.env -f compose.deploy.yml run --rm --no-deps app alembic upgrade head
docker compose --env-file .deploy/local.env -f compose.deploy.yml up -d --no-build --wait
docker compose --env-file .deploy/local.env -f compose.deploy.yml ps
```

访问 http://localhost:18000 。本环境使用 `meta-creative-local` 项目、独立数据库卷和 `.deploy/local/` 文件目录，
不读取原项目 `config.json` 或 `.env.local`，没有 AI Key。不要手动把正式数据复制到这里。

Linux/WSL 可以用包装脚本执行同样流程：

```bash
python3 scripts/init-local.py
bash scripts/deploy.sh .deploy/local.env check
bash scripts/deploy.sh .deploy/local.env build
bash scripts/deploy.sh .deploy/local.env db
bash scripts/deploy.sh .deploy/local.env migrate
bash scripts/deploy.sh .deploy/local.env start
bash scripts/deploy.sh .deploy/local.env smoke
```

`smoke` 只读取页面、健康接口、产品列表和 6 套提示词，不调用付费 AI。
`/api/health` 仅是进程存活检查；Compose 的应用健康检查另读产品列表，以验证数据库和表可用。

停止本地环境（保留数据）：

```bash
docker compose --env-file .deploy/local.env -f compose.deploy.yml down
```

不要加 `-v`，它会删除该项目的数据卷。环境文件不能删后重新生成来重置数据库密码：已有数据库卷仍保留旧密码。

## 环境隔离与后续计划

| 项目 | 本地 | 测试（待建） | 正式（现有） |
|---|---|---|---|
| Compose 项目 | meta-creative-local | meta-creative-staging | meta-creative-deploy |
| 域名 | localhost:18000 | test.wanghongyu.online | wanghongyu.online |
| 数据与密钥 | 独立 | 必须独立 | 保留现有 |

每个环境用自己的 env 文件，分别设置 COMPOSE_PROJECT_NAME、APP_IMAGE、APP_PORT、RUNTIME_DIR。
数据库名相同也可以隔离，因为它们属于不同的 PostgreSQL 容器和卷。
同主机仅运行一个占用 80/443 的 Caddy；本 HTTPS 文件用于单环境主机，不能原样为同机测试再启动第二个 Caddy。
同机测试需设计共享入口及独立网络，或使用另一台测试服务器。

## 与现有正式服的差异（升级前必读）

1. 默认项目名、pgdata、caddy_data、caddy_config 卷名和默认文件挂载路径保持原部署约定。
   升级前仍需用 `docker volume ls` 和实际配置核对，不能仅凭名称假定数据位置。
2. 应用启动不再自动迁移。发布时先备份并验证迁移，再启动新应用；普通重启不改表。
3. Caddyfile 现在从 SITE_ADDRESS 读取域名，正式服环境文件必须补 `SITE_ADDRESS=wanghongyu.online`。
4. 镜像从前端源码构建，不依赖 Git 中的 web/dist。此前的线上 Dockerfile 使用已有 dist。
5. 不要直接在服务器 git pull 覆盖手写配置。先备份这些部署文件，核对路径、密码和卷名，再安排受控发布。
6. `deploy.env.example` 密码是占位符，必须替换。当前连接串直接插值，请使用随机十六进制密码，避免 URL 特殊字符。
7. env 文件中的数据库账号必须与现有卷一致；改 env 不会自动改变已初始化 PostgreSQL 的账号密码。
8. 本阶段不添加认证。线上仍为共享应用，HTTPS 不等于用户权限隔离。

## 预定发布顺序

本地功能分支 → PR 自动检查 → 构建带提交标识的镜像 → 测试环境验收 → 批准同一镜像进入正式环境。
后续流水线应从镜像仓库拉取已验收镜像，正式服务器不重新 build。
正式发布前需处理运行中的 AI 任务；当前重启会中断任务。
回滚应用镜像不等于回滚数据库，数据库迁移需向后兼容并单独制定恢复方案。

本阶段的 smoke 仅证明部署链路与基础数据可用，不替代业务回归、权限测试或真实 AI 验收。

2026-09-17 构建时 npm ci 报告现有依赖有 4 项审计告警（3 moderate、1 high）；需要在下一阶段
用 npm audit 逐项分析开发依赖/运行依赖影响并升级验证，未执行 npm audit fix --force。

## 第二阶段第一步：GitHub 自动检查

`.github/workflows/ci.yml` 在面向 main/develop 的 PR、main/develop 推送时运行，也支持手动触发。
在 GitHub 临时 runner 内生成独立随机数据库凭据，从源码构建镜像、创建空 PostgreSQL 数据库，
执行迁移两次后启动应用，检查只读 smoke 及 `tests/test_deployment.py` HTTP 集成用例。
这不是常驻测试服，不访问阿里云，也不向正式环境发布。

集成用例验证产品/任务创建、默认品牌继承、修改后重新读取、列表可见性、6 套提示词、
无效输入和不存在任务的错误响应。它会在临时数据库创建测试记录，不调用 AI。
本地复现（先启动上述独立本地栈）：

```bash
python3 -m unittest discover -s tests -p 'test_deployment.py' -v
```

默认目标为 http://127.0.0.1:18000，只接受 loopback 地址，并在检测到 AI Key 时拒绝写测试数据。
它不是完整业务测试，不覆盖真实生图、图片版本链或用户权限；本地跑完记录会保留，CI 则销毁临时卷。
CI 的 `down -v` 只用于 GitHub 一次性 runner，不应复制到正式服执行。
Actions 默认仅有 contents:read 权限，不使用部署密钥，checkout 固定到提交 SHA 且不保留 Git 凭据。
