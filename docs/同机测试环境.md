# 同机测试环境

目标：在现有 ECS 上运行独立测试栈，通过现有 Caddy 提供 test.wanghongyu.online，正式应用不更新。
当前文件为已准备方案；是否已部署需看发布记录，不要把 CI 临时环境当作服务器测试服。

## 隔离范围

- 固定 Compose 项目 meta-creative-staging，与现有 meta-creative-deploy 分开。
- 独立 PG 卷 meta-creative-staging_pgdata、独立账号、独立 .deploy/staging 目录，初始化不复制 API Key。
- PG 仅接内部 database 网络，没有主机端口。测试应用接 database 和 edge 网络。
- 现有 Caddy 加入 edge 网络后可以访问 staging-app，但不加入测试数据库网络。
- 应用仅绑定主机 127.0.0.1:18001，安全组无需开放 18001。
- Caddy 使用另一份域名配置，保留原正式域名配置；不运行第二个占用 80/443 的 Caddy。
- 测试 app 内存上限 384MiB，PG 上限 256MiB，限制仅约束测试栈，不能保证正式服资源可用。
- 同机仍共享磁盘、宿主机和 Docker，不能视为生产级故障隔离；测试 OOM、磁盘耗尽和负载需监控。
- noindex 只是请求搜索引擎不收录，不是访问控制。认证前仅使用测试数据，不接入正式付费 Key。

## 部署前检查

1. `free -m`、`df -h /`、`docker stats --no-stream` 确认余量；预留至少约 800MiB 可用内存、5GiB 磁盘只是起步门槛，仍需实际监测。
2. GoDaddy 增加 A 记录 test → 47.238.106.158。80/443 使用现有安全组规则。
3. 备份正式服的 Caddyfile 和两份 Compose，记录正式容器和卷名。不要在正式目录直接覆盖部署基座 PR 的文件。
4. 只使用已通过 CI 的镜像。GitHub Actions 成功运行会上传 deployment-<commit> 制品，包含 application-image.tar.gz、SOURCE_COMMIT、IMAGE_ID 和 SHA256SUMS。
   从本机 `gh run download RUN_ID -n deployment-COMMIT` 下载后用 scp 传服务器；不要把 GitHub 写权限 Token 放到正式服务器。

## 初始化测试栈（以下在服务器项目根目录）

先把 `compose.staging.yml`、`compose.staging-edge.yml`、`deploy/staging.caddy`、`scripts/init-staging.py`、`scripts/staging.sh`
复制到正式项目根目录对应路径。这些新文件不替换旧 Compose/Caddyfile，也不包含密码。

在制品目录先执行 `sha256sum -c SHA256SUMS`，校验成功才 `docker load -i application-image.tar.gz`。
用 `docker image inspect --format '{{.Id}}' meta-creative-tool:sha-COMMIT` 对比 IMAGE_ID，确认加载的是测试通过的镜像。
`COMMIT` 必须替换为 SOURCE_COMMIT 中的完整提交 SHA，然后回到项目根目录：

```bash
python3 scripts/init-staging.py meta-creative-tool:sha-COMMIT
bash scripts/staging.sh check
bash scripts/staging.sh db
bash scripts/staging.sh migrate
bash scripts/staging.sh start
curl -fsS http://127.0.0.1:18001/api/health
curl -fsS http://127.0.0.1:18001/api/products
```

初始化脚本只创建缺失配置，不覆盖已有密码和镜像版本。后续版本仅更新 staging.env 的 STAGING_IMAGE，不能删除重建凭据。

## 接入现有 Caddy（先验证测试服务，再做这一步）

原正式 Caddyfile 保持原来的 wanghongyu.online 段，只在文件末尾添加一次：

```caddy
import /etc/caddy/sites/*.caddy
```

先备份原 Caddyfile。共享入口的 Compose 使用当前服务器原文件，末尾追加第三份 override：

```bash
docker compose --env-file .env.local -f compose.deploy.yml -f compose.https.yml -f compose.staging-edge.yml config -q
docker compose --env-file .env.local -f compose.deploy.yml -f compose.https.yml -f compose.staging-edge.yml run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose --env-file .env.local -f compose.deploy.yml -f compose.https.yml -f compose.staging-edge.yml up -d --no-deps caddy
```

这会短暂重建 Caddy，正式 app/PG 不重启。以后管理共享入口要始终带这三份文件，否则会丢失测试网络/配置挂载。
验证两个域名首页及 /api/health，测试域名应有 X-Deployment-Environment: staging 响应头。
证书失败时查看 Caddy 日志，不要删除证书卷反复申请。

回退入口：还原备份的 Caddyfile，再使用原两份 Compose `up -d --no-deps caddy`；测试可单独 `bash scripts/staging.sh stop`。
禁止用 `down -v` 处理测试问题，尤其不能在正式 Compose 项目执行；已有 Caddy 连接测试网络时也不要随意删除该网络。
